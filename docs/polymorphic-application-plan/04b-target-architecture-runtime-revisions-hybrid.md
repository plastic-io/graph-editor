# 4. Target architecture (part B: runtime containment, revisions, hybrid execution)

## 4.6 Runtime isolation, scheduling and budgets

### 4.6.1 What each existing boundary is and what it protects against [FACT]

| Boundary | Where it exists today | Protects against | Does NOT protect against |
|---|---|---|---|
| Browser Web Worker | editor scheduler (GE-35) | blocking the UI thread; DOM access from `set` code | network/IndexedDB access, infinite loops (worker keeps spinning; `panic` only trips the next edge, RT-42), memory growth |
| Node `worker_threads` Worker | server per request (A2 F.2) | crashing the Lambda process on an uncaught error | anything else: shares credentials, filesystem, network; `require` available (GS-29); no `resourceLimits` set |
| V8 isolate | Rust runtime only, one per node execution (RT-25) | cross-node JS state leakage | CPU loops (no `terminate_execution`), heap growth (default `CreateParams`, fatal OOM exit 133, RT-35), process exit on bad url (RT-33) |
| OS thread | Rust: none dedicated (caller thread, nested isolates RT-30); TS: Worker thread | — | a blocked thread blocks everything on it |
| Tokio task | Rust: tests only (RT-36) | — | — |
| Process / Lambda | one Lambda invocation per request (1024 MB, 30 s, GS-A.3) | runaway CPU beyond 30 s (Lambda kills the sandbox); memory beyond 1 GB | cost, cross-request state (module-level caches survive warm starts, GS-33), anything inside the 30 s |
| Deployment boundary | one AWS account, one role for all Lambdas | — | tenant separation (none) |

A Tokio timeout or a rejected promise is not evidence that JS stopped: in TS the loop keeps running on the Worker thread; in Rust the loop keeps the caller thread. Only V8 `TerminateExecution` (or process death) stops a tight loop.

### 4.6.2 Target execution model per domain (decision D-4)

**Server (TS scheduler, milestone M1–M3):** run the scheduler *inside* an `isolated-vm` isolate per execution (`new ivm.Isolate({memoryLimit: MB})`), with the host side of `edges`/`host` bindings exposed as `ivm.Reference`/`ivm.Callback`s and values copied (`ExternalCopy`). isolated-vm is the containment mechanism because it (a) is a real V8 isolate with no Node API inside, satisfying "edges are the only bindings" by construction; (b) exposes `isolate.dispose()`, per-`script.run({timeout})` wall limits, `isolate.cpuTime`/`wallTime`, and `memoryLimit` with a catchable `Isolate was disposed`/OOM error on the host side; (c) works inside the existing per-request `worker_threads` Worker so the Lambda parent survives an isolate death. Cost: a native addon (21 MB, measured) built on the Lambda image and shipped as a layer or container image; isolate creation 1–2 ms (measured); real cold-start delta not yet measured. **Spike S-1 (done, `spikes/S-1-report.md`) confirmed the build on the Lambda Node 22 image (isolated-vm 6.x needs Node ≥ 22, so the runtime moves to nodejs22.x, Q-5).** Fallback if S-1 fails: `worker_threads` with `resourceLimits: {maxOldGenerationSizeMb, maxYoungGenerationSizeMb, codeRangeSizeMb, stackSizeMb}` + `worker.terminate()` from a host watchdog, plus a hardened loader that never passes `require`/`AWS`/`openai` (this removes *convenience* authority but not `process`/`fetch` — documented residual).

Thread model on the server: Lambda handler thread (owner) → one Worker thread per execution (existing, GS-A2 F.2) → inside it one isolate; the Worker's event loop runs host callbacks; the watchdog timer lives on the Lambda handler thread (not inside the Worker) so a blocked Worker cannot starve its own watchdog. Blocking JS occupies only its Worker thread.

**Browser:** keep the Worker [FACT]; add a host watchdog on the main thread that `worker.terminate()`s on wall budget (the only out-of-band stop available in browsers) and re-creates the worker (the editor already re-instantiates on graph change, GE-36); cooperative hop/fan-out/observation counters inside the patched scheduler.

**Rust (M6, optional):** one isolate per *execution* (not per node, RT-25) with `CreateParams::heap_limits(initial, max)`, `add_near_heap_limit_callback` (raise the limit once, mark `memory-pressure`, then let `set_oom_error_handler` abort the isolate), a watchdog `std::thread` holding `isolate.thread_safe_handle()` that calls `terminate_execution()` on wall budget (rusty_v8 0.32.1 has all four APIs, A4; `request_interrupt` is absent), `only_terminate_in_safe_scope(false)`; run the execution on a dedicated OS thread (`std::thread::spawn`) owned by a Tokio `spawn_blocking` task so the async host can await completion/cancellation; never on a Tokio worker. After `terminate_execution` the isolate is **disposed, not reused**. Fan-out (RT-26) and value transport (RT-29) must be fixed first (PB-131) and the crate upgraded from `rusty_v8` 0.32.1 (V8 9.6, 2021) to `v8` 152.x (A4) with the API renames that implies.

### 4.6.3 Termination plan (concrete)
1. **Cooperative**: the patched scheduler checks a `CancellationToken` (`ExecutionHandle.cancel()` sets it) at every `beginedge` and before every connector dispatch (`Node.ts` setter loop) and rejects with `ExecutionCancelled`; `host.*` calls check it too. This stops well-behaved graphs between hops.
2. **Out-of-band**: the watchdog on the owner thread fires at `budget.wallMs` (and at `cancel()` if cooperative stop did not complete within `graceMs`, default 250): server → `isolate.dispose()` (isolated-vm) or `worker.terminate()` (fallback); browser → `worker.terminate()`; Rust → `IsolateHandle::terminate_execution()` then join the thread with a bounded wait, then drop the isolate.
3. **Stuck native work**: a host binding blocked in native code (e.g. a slow `fetch` in the host) is bounded by its own timeout (`host.fetch` has `AbortSignal` from the token); if the Worker does not exit within `hardKillMs` after termination, the Lambda handler abandons it and returns — Lambda tears the sandbox down at the end of the invocation (30 s cap) — and records `exec.end {reason:'abandoned'}`.
4. **Post-failure handling (measured in S-1)**: after any timeout or memory-limit rejection the isolate may be idle but wedged (a microtask storm leaves it unresponsive to every further call while consuming no CPU); the owner therefore disposes it *immediately* and never calls into it again — statistics are read from `isolate.cpuTime`/`wallTime` (plain properties) or before the run, never after a failure. Isolates are per execution and never reused.
5. **Cleanup**: on any exit the owner emits `exec.end`, releases budget reservations to the parent, deletes the execution's pending `edge.deliver` messages, and marks the `executions/<id>.json` status. Isolates are never reused after cancellation or OOM.
6. **Process-level containment** is Lambda itself (one invocation = one process); a per-tenant Lambda alias/concurrency reservation is the cost-bearing option if noisy tenants appear (not in the first milestones).

### 4.6.4 Hierarchical budgets
```ts
interface BudgetSpec { wallMs; cpuMs?; heapMb; hops; fanOut; depth; observations; observationBytes; effects: { net; storage; secret }; payloadBytes; concurrentChildren; }
```
Levels: tenant (policy document, replenished per minute for rate-like dimensions) → root execution (`graph.invoke.budget` ≤ tenant remaining) → component instance (manifest `budgets` caps, cannot be raised by the consumer) → node/isolate (per-invocation slice). Allocation: the root reserves from the tenant bucket at entry (CAS on `budgets/tenants/<t>.json`, S3 `If-Match`) and releases unused at `exec.end`; children inherit a *slice* (`remaining × share`), cannot mint capacity, and are cancelled with the parent (token is hierarchical). Fan-out across a hyperedge divides `remaining` evenly unless the edge contract declares weights; cross-domain deliveries carry the remaining slice in the message and the receiving domain enforces it locally. Attribution: every observation carries `instancePath`, so shared work is charged to the instance that invoked it.

| Dimension | Enforcement | Type |
|---|---|---|
| wall time | owner watchdog + isolated-vm `timeout` | hard |
| CPU time | isolated-vm `cpuTime` sampled at hops; Lambda cap | hard (server), monitor-only (browser) |
| V8 heap | isolated-vm `memoryLimit` / Rust `heap_limits` | hard |
| external/native memory | `worker.resourceLimits` (fallback) / Lambda memory | hard at process level |
| concurrent isolates/threads | owner semaphore per Lambda (1 today) | hard |
| queued tasks / fan-out / hops / depth | scheduler counters | cooperative (hard when combined with wall) |
| observation count/bytes, payload bytes | observation sink | cooperative + sampling |
| network/storage ops | `host` counters | hard at the binding |
| cloud cost / deployment limits | IaC validator (plan `estimatedCostDelta`), Step Functions timeouts | estimate + hard timeout |

### 4.6.5 Memory pressure and OOM
OOM is not cancellation: it means the isolate is unusable. isolated-vm reports it as an error on the host call; the owner marks `exec.error {reason:'oom'}`, disposes the isolate, does **not** retry automatically, and the Worker/Lambda continue serving (spike S-1 verifies the host survives an isolate OOM at 128 MB). Rust: near-heap-limit callback → one-time raise + flag → OOM handler → abort isolate on its own thread; the host process survives only if V8 is configured not to `FATAL` (requires the `v8` crate upgrade; on 0.32.1 the observed behaviour is process death, RT-35). Adversarial cases and their stop mechanism: CPU loop → wall watchdog; microtask storm → same (microtasks run on the isolate thread); infinite recursion → V8 stack limit → `RangeError` (already observed, RT-08) plus hop budget; unresolved promises → completion tracking (§4.6.6) ends the execution at wall budget with `reason:'pending-promises'`; expensive host calls → per-call timeout; cancellation races → token checked after every host call returns; allocator pressure → heap limit; observation floods → sink caps + sampling.

### 4.6.6 Completion, handles, states
[FACT] In 2.0.3 `url()` resolves after the entry node's synchronous prefix; nothing signals when async work is done (RT-07). The patched scheduler (PB-060, released as 2.1.0 and pinned by both consumers, PB-061) tracks in-flight promises (`parseAndRun`, connector `edgeExecute`) in an `ExecutionScope` counter and emits `end` only when the counter reaches zero or the budget expires; `url()` returns an `ExecutionHandle`.
```ts
interface ExecutionHandle { executionId; revisionId; owner; state: 'queued'|'running'|'cancelling'|'completed'|'failed'|'cancelled'|'abandoned'; cancel(reason): Promise<void>; done: Promise<ExecutionResult>; budget: BudgetView; }
```
State diagram: appendix A10.3. State machine: `queued →(reserve budget) running →(all spans done) completed | →(error) failed | →(cancel: cooperative) cancelling →(exited) cancelled | →(watchdog) cancelling →(terminated) cancelled | →(hard kill timeout) abandoned`. Acceptance criteria (thresholds **measured in S-1 on the Lambda Node 22 image**, `spikes/S-1-report.md`: loops stopped ≤ 10 ms past budget, 128 MB limit contained with the host surviving, no leak over 60 adversarial runs): a `while(true){}` node is stopped within `wallMs + 100 ms`; a 200 MB allocation loop is stopped by a 128 MB limit without Lambda failure; two executions with equal budgets on one Lambda get ±20 % CPU share; after 1 000 cancellations no Worker/isolate leaks (RSS stable ±10 %); `exec.end` always emitted (100 % in the adversarial suite).

## 4.7 Revisions, proposals, activation, replay, rollback

### 4.7.1 Revision = named immutable cut of the update log
```ts
interface Revision { revisionId: string /* ulid */; graphId: string; parent?: string; stateVector: string /* base64 */; headUpdateId: string; digest: { definition: string; layout: string; full: string } /* sha256 of canonical projections */; schemaVersion: number; pins: { components: { publishedId; version; digest }[]; runtime: { scheduler: string } }; mutationIds: string[] /* since parent */; createdBy: PrincipalRef; at: string; label?: string; proposalId?: string; }
```
Created by `revision.commit` (explicit, human or agent with `graph:commit`) or automatically when a proposal is committed. Stored immutable (`If-None-Match:*`); `revisions/<graphId>/HEAD` is a CAS pointer (`If-Match` ETag). Verification: reconstruct the doc from snapshot + updates up to `headUpdateId` [FACT `updatesUpTo`, GS-A2 D.3] and compare digests. Compaction: snapshots may fold updates [FACT], but updates referenced by a retained revision's `(stateVector, headUpdateId)` are kept until a *revision snapshot* (`revisions/<graphId>/<revisionId>.snapshot.bin`, the full V2 state at that point) is written; then older updates can be lifecycle-deleted without losing reconstruction; the audit log keeps the per-mutation records regardless.

### 4.7.2 Mutation/proposal lifecycle
State diagram: appendix A10.4.
```
draft ─(proposal.create)→ validated ─(policy says review)→ awaiting-review ─(decide approve)→ approved ─(commit)→ committed ─(activate)→ activating → active
   │                           │                                   └(decide reject)→ rejected
   │                           └(simulate/shadow)→ simulated (result attached) ─┐
   └ expired (ttl) / cancelled (proposer)                                       ▼ back to validated/awaiting-review
 committed ─(activation failed)→ failed ; active ─(rollback)→ rolled-back | compensated
```
Owners: proposer (create/cancel), admission service (validated/expired), approver with `graph:approve` (decide), committer with `graph:commit` (commit — the proposer may commit only if policy allows self-commit), activator with `graph:activate`. Durable state: `proposals/<graphId>/<proposalId>.json` (CAS on ETag), every transition appended to audit. Retries: commit is idempotent on `proposalId`; activation is idempotent on `(graphId, revisionId)`. Expiry: 7 days default. Crash recovery: a `committed` proposal with no revision object → re-run commit; `activating` with no `active` pointer change → re-run activation (both driven by a sweeper Lambda on a 5-minute schedule and on the next read). Approval binds `{proposalDigest, baseRevision, policyVersion, scope}`; any edit to the proposal or a moved base invalidates it.

### 4.7.3 Semantic diff and provenance
Example diff documents (rename, component upgrade) validated against the `diffSummary` schema: appendix A7.4.
`semanticDiff(before, after)` (in `graph-crdt/diff.ts`, shared) yields typed changes: node add/remove/rename, port changes, edge/connector add/remove (with hyperedge fan-out deltas), code text diffs (line-based), component pin changes, placement, capability requirement deltas (privilege delta flagged), budget deltas, test-ref deltas, IaC desired-state deltas, layout-only changes (collapsed). Impact: consumers of changed published components, nodes downstream of changed edges, contracts that no longer assign. Provenance fields on `MutationRecord`: actor, delegatedBy, rationale (agent-supplied, untrusted text), parentRevision, tool/session id (MCP `clientInfo`, editor `workstationId`), timestamps, validation result, decisions, execution/deployment links. Tamper evidence: audit objects are immutable and hash-chained per graph (`prevHash` field); this is *evidence of ordering*, not cryptographic provenance. Signatures (decision D-10): if required, sign `ComponentManifest.digest` and `Revision.digest.full` with a KMS asymmetric key held by the server role (`kms:Sign` scoped to one key), verify on read; clients never sign.

### 4.7.4 Commit vs activation, consistency, in-flight work
Commit = HEAD pointer moves to a revision (CAS). Activation = `active/<graphId>` pointer moves (CAS) **and** the projection for that revision is written to `revisions/<graphId>/<revisionId>.projection.json`; executors read `active/<graphId>` → projection (replacing today's `graphs/projections/endpoints/<url>.json` lookup, GS-27; the endpoint index becomes `endpoints/<url> → {graphId}` and is updated at activation only). Live editing continues in the doc without affecting execution. Replicas learn of activation via a `revision.activated` message on `graph-notify-{id}` and via MCP `notifications/resources/updated`. Scheduler caches are keyed by `revisionId`, so a stale cache can only run an older *committed* revision, never live state. Linearization of concurrent proposals: HEAD CAS serialises commits; the loser gets `STALE_BASE`. In-flight executions keep the revision they started with (`ExecutionHandle.revisionId`); activation strategy `switch-new-work` (default) lets them drain; `cancel-inflight` cancels them via handles listed in `executions/active/<graphId>/`. If commit succeeds but fan-out/notification fails, the pointer is the truth: readers reconcile on next read, the sweeper re-emits notifications. Browser/server schema skew: the projection carries `schemaVersion`; an executor that does not support it refuses to activate (`UNSUPPORTED_SCHEMA`) and the editor shows which domain lags.

### 4.7.5 Replay, simulation, shadow
- Structural replay: rebuild any revision from the log (always possible).
- Deterministic execution replay: possible only for executions recorded with `capture: full` on inputs and whose effects were recorded (`host` records effect responses when `record: true`); time/randomness are provided through `host.now()`/`host.random()` so replays can substitute them. Otherwise replay reconstructs *evidence* (the observation stream), not results.
- Effects are never re-executed in replay; `host` in replay mode returns recorded responses or `EffectUnavailableInReplay`.
- Simulation classes by capability: `net:https` → recorded responses or mocks from the component's fixtures; `storage:*` → isolated prefix `sim/<proposalId>/`; `secret` → denied; `aws:*` → `iac.plan` only (change set, never execute); `browser:dom` → skipped (server simulation) or run in the proposer's browser with a sandbox flag. Shadow execution runs the proposed revision against recorded inputs of recent executions with effects in `sim` mode and compares outputs per contract (`equal`, `schema-equal`, `diff`); differences and unsimulated effects are listed. Required when the diff touches `code`, `capabilities`, `placement` or `iac`; skippable for `layout`-only; unsafe (refused) when a required effect has no simulation class.

### 4.7.6 Rollback per layer
Definition rollback = commit a new revision whose content equals the target (history is never rewritten); activation rollback = move `active` to an older revision (no new commit needed); application state (`storage:kv` data) = not rolled back automatically; compensation = run the component's declared compensator (a test-like graph entry) if any; infrastructure = IaC desired-state revert triggers a new plan/apply (a CloudFormation update back to the old template, which may not restore data). Irreversible effects (payments, emails, deletions) are flagged by capability metadata `irreversible: true` and listed in the rollback report; forward recovery is the default recommendation. Residual drift is written as `observed/drift` and shown in the editor status bar until acknowledged.

## 4.8 Hybrid execution across browser and server

### 4.8.1 Placement contract
`node.properties.placement ∈ {'browser','server','portable'}` (manifest carries the definition's constraint; instance may narrow, never widen). Derivation during migration: nodes with `template.vue` or `browser:dom` capability → `browser`; nodes with `server`-only capabilities (`aws:*`, `secret`, `storage:s3`) → `server`; else `portable` (runs where invoked). Serialisation across a boundary: the `wireValue` codec (§4.3.5) — JSON only; no functions, no DOM nodes, no `secretRef` resolution (a `secretRef` string may cross but resolves only on the server), values above `payloadBytes` budget are rejected. What travels: `{executionId, spanId, seq, revisionId, instancePath, connectorId, field, value, budgetSlice, correlationId}` and the *owner principal id* (server-derived on receipt; never the token). Browser visibility never implies server credentials: the browser has no `host` bindings for `aws:*`/`secret`, and the server derives the executing principal from the connection, not from the message.

### 4.8.2 Ownership and the `edge.deliver` protocol
Rule: **the domain whose placement matches executes; every other replica observes.** A server-owned execution reaching a browser-placed node emits `edge.deliver` on `graph-notify-{graphId}` addressed by `target: {sessions: 'initiator'|'all-viewers'}`; UI/visualisation nodes default to `all-viewers` (each viewer renders its own copy — correct for a shader; dedup key `(executionId, connectorId, seq)` prevents double-render on reconnect replay); nodes whose browser side performs an external effect must be `initiator`-targeted and are executed by exactly the initiating session (if it is gone, the delivery is parked in `executions/<id>/pending/` for `deliveryTtl`, then `exec.error {reason:'no-browser'}`). A browser-owned execution reaching a server-placed node sends `edge.deliver` over the WS (replacing today's `executeGraph`, GE-41) with its `executionId`; the server executes with the *connection's* principal, once (idempotency table `executions/<executionId>/deliveries/<connectorId>-<seq>` with `If-None-Match:*`), and returns results as `edge.deliver` back. Multiple editors connected: they all observe; only the owner executes. Disconnect/reconnect: the browser resends `SyncStep1` and `executions.resume {since: lastSeq}`; the server replays pending deliveries from the durable queue. Server restart / Lambda timeout: the execution record has a lease (`executions/<id>.json` with `leaseUntil`); a new Lambda may resume server-side work only for `restartable: true` nodes (pure/portable); effect nodes are not re-run — the execution fails with `reason:'timeout'` and compensation guidance. Migration between runtime instances is not supported in the first releases (documented).

### 4.8.3 Hyperedge semantics across domains
[FACT] in-process: fan-out in connector order, fire-and-forget in 2.0.3, no join, no dedup (RT-06/08). Target: ordering per edge is connector order; delivery at-least-once with dedup keys; correlation via `executionId/spanId/causationId`; per-connector timeout from the budget slice; partial failure = other connectors continue, the execution ends `failed` with the list of failed connectors (no automatic retry of effect nodes; pure nodes may `retry: n` per contract); backpressure = `concurrentChildren` budget; cancellation propagates through the token and via `execution.cancel` messages to the other domain; budget slices propagate in the message. Mixed-domain work is **not atomic**; observable intermediate states are the observations themselves; compensation is per component (4.7.6). Exactly-once is not promised anywhere; effect nodes get idempotency keys derived from `(executionId, spanId)` which they must pass to external systems that support them.

### 4.8.4 Structure changes vs running executions
Work is pinned to `revisionId` at entry; new work uses the active revision; `activate` strategies: `switch-new-work` (default), `drain` (wait for in-flight ≤ `drainMs`), `cancel-inflight`. Browser previews (the editor's local worker) run the *live* snapshot as today, labelled "preview (unactivated)" in the UI; the server never does.
