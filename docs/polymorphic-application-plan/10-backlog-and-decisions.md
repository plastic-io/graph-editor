| D-21 | Effective capabilities = instance ∩ manifest ∩ principal, in that order; a bare kind grants nothing; the refusing layer is named in the error and the observation; only privileged kinds (`secret`) reach the audit chain, every other effect is an observation | union of grants, or audit every effect | laundering through nesting is impossible by construction; the audit chain stays small and the observation store carries the volume | decided 2026-09-21 (PB-050/051/056) |

| D-23 | Browser executions report themselves to the server when they end, and the server stamps identity, graph and domain rather than trusting the body, caps volume and keeps the first report of an execution | trust the client's record, or keep browser observations in the browser | observations are how anyone (a human or an agent) finds out what a graph did, and half the graph runs where the store cannot be written; treating the report as evidence rather than as state keeps a client from writing history for someone else | decided 2026-09-21 (PB-053/054) |
| D-24 | Containment is chosen per node (`properties.containment`), the graph or the deployment supply the default, and the deployed default stays `worker` until graphs are migrated; a node that asks for containment and cannot get it fails rather than running uncontained | contain everything on the server at once | the dev stage runs 2.0 graphs that use `this.openai`, `AWS` and `require`, and none of them survive a realm with no ambient authority; failing closed is what keeps the setting meaningful while both kinds coexist | decided 2026-09-21 (PB-062) |
| D-25 | The scheduler gains `options.executeNode` (2.2.0) rather than the server reimplementing traversal: the scheduler still decides what runs and in what order, the runtime decides where the code runs | run the whole scheduler inside the isolate, or fork the traversal into the server | one traversal implementation keeps browser and server behaviour identical, and containment becomes a property of the deployment rather than of the graph engine | decided 2026-09-21 (PB-062) |
| D-26 | Hybrid delivery is asymmetric on purpose: server → browser is a hand-off with no reply (the browser owns what happens next), browser → server is a request that answers with the node's output edges | make both directions symmetrical, or run a coordinator that owns the whole execution | the shapes are genuinely different: a browser node may be rendered by many viewers at once and none of them owes the server an answer, while a browser that reaches a server node has one execution to continue and needs the values back to continue it | decided 2026-09-21 (PB-071) |
| D-27 | Observations from a domain that does not own an execution are stored beside the owner's record (a delivery's own file, or one report per browser session) and joined when anyone asks what the execution did | let the owner's record be overwritten, or keep each domain's observations separate | an execution is one story even when two runtimes wrote it, and neither domain can be trusted to rewrite the other's half | decided 2026-09-21 (PB-054/071) |
