# 4. Target architecture (part C: IaC component, substrate evolution)

## 4.9 CloudFormation as a privileged graph component

### 4.9.1 What exists today [FACT]
Serverless v3 drives CloudFormation from a developer laptop (`npx serverless deploy`, templates in `.serverless/`); the Lambda role grants logs, S3 on one bucket, `execute-api:ManageConnections`, one Secrets Manager secret and one layer — **no** `cloudformation:*`, `codebuild:*`, `iam:*`, `sts:AssumeRole`, `events:*`, `states:*` (GS-02, 0 template hits). No CodeBuild project, no CFN SDK call, no EventBridge rule, no Step Functions, no status plumbing exists. Everything below is proposed; the current role *cannot* deploy anything, which is the correct starting posture: the request-serving Lambda must never hold CloudFormation authority directly.

### 4.9.2 Component model
`IacStack` is a published component (`kind:'node'`, `placement:'server'`, capability `aws:cfn` with a stack-prefix scope) instantiated once per managed stack. Its `template.set` is not user JS: it is the builtin `host.deploy(desired)` (the node's manifest has `builtin: 'aws.cloudformation'`; the executor refuses to run user code for builtin nodes). Parameter assembly lives in the instance's nested graph like any other logic.

**Desired-state input** (edge `desired`, JSON Schema 2020-12, `additionalProperties:false` throughout):
```ts
interface IacDesiredState {
  schemaVersion: 1;
  stack: { name: string /* ^[A-Za-z][A-Za-z0-9-]{0,127}$ and must start with the environment's allowed prefix */; account: string; region: string; environment: 'dev'|'staging'|'prod' };
  template: { artifactRef: { graphId: string; nodeId: string; revisionId: string; sha256: string }; format: 'yaml'|'json' };   // immutable S3 object written at revision commit
  parameters: Record<string, string | { secretRef: string }>;
  capabilities: Array<'CAPABILITY_IAM'|'CAPABILITY_NAMED_IAM'|'CAPABILITY_AUTO_EXPAND'>;
  operation: 'plan'|'apply'|'destroy'|'cancel'|'detect-drift';
  trigger: { kind: 'explicit'; approvalRef?: string } | { kind: 'reconcile'; sourceRevision: string };
  build?: { project: string; sourceArtifactRef: ArtifactRef; buildspecArtifactRef: ArtifactRef };
  correlation: { proposalId?: string; idempotencyKey: string /* ulid */ };
}
```
Server-derived (never trusted from the edge value): actor, `revisionId` of the admitted mutation that carried the desired state, approval validity, account/region allow-list membership, policy version.

**Observed outputs** (edge `observed`, discriminated union): `validation {ok, errors[], templateSha256, desiredRevision}`, `plan {changeSetId, changes[], destructive, estimatedCostDelta?}`, `build {buildId, status: IN_PROGRESS|SUCCEEDED|FAILED|FAULT|STOPPED|TIMED_OUT, logRef}`, `deploy {operationId, stackId?, status: <CFN stack status>, reason?, at}`, `outputs {stackOutputs, resources[{logicalId,type,physicalId,retained}]}`, `drift {driftStatus, driftedResources[]}`, `terminal {outcome: succeeded|failed|rolled-back|rollback-failed|cancelled|superseded, effectiveRevision, requestedRevision, manualRecoveryRequired}`. Each value is simultaneously (a) emitted on the output edge, (b) an `Observation {kind:'deploy.status'}`, and (c) folded into the durable status document `iac/stacks/<account>/<region>/<name>/status.json` (CAS) and mirrored read-only into the doc at `observed/iac/<instanceId>` so a subscriber that reconnects later recovers the current state without the live stream (R-13.7).

### 4.9.3 Initiation rules, loops, serialization, idempotency
- Only `trigger.kind:'explicit'` values arriving on `desired` start an operation; `reconcile` triggers are minted by the activation step when a revision changes a `desired` value (never by the observed mirror).
- Loop prevention: writes to `observed/*` are made by principal `system:iac` and are excluded from the reconciler's change detection; `observed` is never an input of `desired` (validator rejects a connector from any `observed` output into an `IacStack.desired` input).
- Stack-level serialization: one in-flight operation per `{account, region, name}` via `iac/stacks/…/lock.json` written with `If-None-Match:*` (S3 conditional writes, verified A4) and a TTL; a newer desired state while running is queued as `superseded-pending`, coalesced, and applied after the terminal state; superseded intermediates get `terminal {outcome:'superseded'}`.
- Idempotency: `correlation.idempotencyKey` = CloudFormation `ClientRequestToken` on `CreateChangeSet/ExecuteChangeSet/DeleteStack` and = the Step Functions execution `name` (idempotent for STANDARD workflows, A4), so retries cannot start a second AWS operation.
- Out-of-order feedback: the status document stores `operationId → {clientRequestToken, requestedRevision}`; EventBridge events (at-least-once, A4) carry `stack-id`; events whose timestamp precedes the current operation's start are recorded but do not regress status.

### 4.9.4 Lifecycle (state machine; owner in brackets)
State diagram: appendix A10.5; CloudFormation/CodeBuild status mapping: appendix A6.
`requested[admission] → validating[orchestrator] → (invalid → failed) → planning (CreateChangeSet; wait) → awaiting-review (if plan.destructive || env policy) [human/agent with iac:approve] → (rejected → cancelled) → building (optional CodeBuild) → (build failed → failed) → executing (ExecuteChangeSet) → observing (EventBridge + poll fallback) → succeeded | failed | rolled-back (UPDATE_ROLLBACK_COMPLETE) | rollback-failed (UPDATE_ROLLBACK_FAILED, manualRecoveryRequired) | cancelled | superseded`. CodeBuild states are mapped separately from CloudFormation stack statuses (exact mapping table in appendix A6); build success is a precondition of `executing`, never a deployment status. CodeBuild is needed only when `build` is present (source needs compiling/packaging); a plain template deploy skips it.

### 4.9.5 Durable orchestration (decision D-2 context: S3-only substrate + one new managed service)
Verified constraints: Lambda ≤ 900 s, REST integration ≤ 29 s default, WS ≤ 2 h / 10 min idle, CloudFormation → EventBridge at-least-once (A4). Proposal: an **AWS Step Functions Standard** state machine `plastic-io-iac-orchestrator-<env>` started by the server's `iacService` (`name = idempotencyKey`). Steps: Validate → CreateChangeSet → WaitForChangeSet (EventBridge rule `CloudFormation Stack Status Change`/`Resource Status Change` → `SendTaskSuccess` callback; 60 s `DescribeChangeSet` poll fallback) → Choice(review) → optional `codebuild:startBuild.sync` → ExecuteChangeSet → WaitForStack (callback + 60 s `DescribeStacks` poll, `TimeoutSeconds` 14 400) → Publish (invoke server `iacFeedback` Lambda → status doc + observation + WS fan-out + doc mirror). Retries `IntervalSeconds 10, BackoffRate 2, MaxAttempts 5` on throttling; every transition checkpointed by Step Functions history and mirrored to `iac/operations/<operationId>/state.json`; on timeout → `failed` with `manualRecoveryRequired` if the stack is non-terminal. Alternative considered: Lambda + S3 + EventBridge only (rejected for M4: re-implements retries/timeouts/dedup Step Functions gives, same IAM footprint). Spike S-5 measures EventBridge callback latency vs polling.

### 4.9.6 Deliberate AWS authority (full JSON policy documents in appendix A8; placeholders `${ACCOUNT}`, `${REGION}`, `${ENV}`, `${STACK_PREFIX}`, role ARNs)
1. **Request-serving role** (existing `IamRoleLambdaExecution`): add only `states:StartExecution` on `arn:aws:states:${REGION}:${ACCOUNT}:stateMachine:plastic-io-iac-orchestrator-${ENV}` and `states:DescribeExecution`, `states:StopExecution` on `…:execution:plastic-io-iac-orchestrator-${ENV}:*`. It never touches CloudFormation.
2. **Orchestrator role**: `cloudformation:CreateChangeSet, DescribeChangeSet, ExecuteChangeSet, DeleteChangeSet, DescribeStacks, DescribeStackEvents, DetectStackDrift, DescribeStackDriftDetectionStatus, DescribeStackResourceDrifts, CancelUpdateStack, ContinueUpdateRollback, DeleteStack` on `arn:aws:cloudformation:${REGION}:${ACCOUNT}:stack/${STACK_PREFIX}*/*`, condition `"StringEquals": {"cloudformation:RoleArn": "${CFN_EXEC_ROLE_ARN}"}` (every operation must use the execution role) and `"ForAllValues:StringLike": {"cloudformation:TemplateUrl": "https://${ARTIFACT_BUCKET}.s3.${REGION}.amazonaws.com/iac/templates/*"}`; `s3:GetObject` on `${ARTIFACT_BUCKET}/iac/*`; `codebuild:StartBuild, BatchGetBuilds, StopBuild` on `arn:aws:codebuild:${REGION}:${ACCOUNT}:project/plastic-io-iac-${ENV}`; `iam:PassRole` **only** on `${CFN_EXEC_ROLE_ARN}` with `"StringEquals": {"iam:PassedToService": "cloudformation.amazonaws.com"}`; `lambda:InvokeFunction` on the feedback function; `events:PutTargets` not needed (static rules).
3. **CloudFormation execution role** (`${CFN_EXEC_ROLE_ARN}`; trust `cloudformation.amazonaws.com` with `aws:SourceAccount`): resource-creating actions per environment allow-list (`lambda:*`, `apigateway:*`, `s3:*` on `${STACK_PREFIX}*` names, `logs:*`, `dynamodb:*` on prefixed tables, `iam:CreateRole/DeleteRole/AttachRolePolicy/PutRolePolicy/PassRole` **only** with `"StringEquals": {"iam:PermissionsBoundary": "${BOUNDARY_ARN}"}`), plus explicit `Deny` on `iam:*` without the boundary, `organizations:*`, `account:*`, `sts:AssumeRole` to non-prefixed roles, and `cloudformation:*` on the substrate stacks (`plastic-io-graph-server*`, `plastic-io-iac-orchestrator*`) — the self-modification guard. Wildcards on service actions are the one place AWS semantics require them (CloudFormation needs the union of what its resources need); the mitigations are the boundary, name-prefix scoping and the denies.
4. **CodeBuild service role**: `logs:*` on its group, `s3:GetObject` on `iac/sources/*`, `s3:PutObject` on `iac/build-outputs/*`; no `cloudformation:*`; `privilegedMode:false`; no VPC egress beyond package registries (egress allow-list is an [OPEN] policy item).
5. **Client/agent authority**: none of the above; only graph capabilities (`iac:propose`, `iac:approve`, `iac:read-status`) enforced by admission; AWS credentials never leave the server side; credential lifetime = the Lambda/Step Functions role session.

Escalation analysis: templates creating IAM → bounded by the permissions boundary and named-IAM approval (`CAPABILITY_NAMED_IAM` requires a human `iac:approve`); custom resources and macros execute code with the execution role's authority → validator rejects `Custom::*`, `AWS::CloudFormation::CustomResource` and `Transform` unless the environment policy allow-lists them; build commands are arbitrary shell → CodeBuild role is minimal and has no CFN rights; resource policies granting `Principal:"*"` or foreign accounts → validator denies unless allow-listed; secrets enter only as `NoEcho` parameters resolved by the orchestrator from `secretRef`, never echoed into observations. The IaC component cannot change its own guardrails: the validator policy and IAM are substrate configuration (§4.10), not graph content.

### 4.9.7 Failure feedback and cancellation
`iac.cancel` marks `cancel-requested`: `planning` → delete the change set; `executing` → `CancelUpdateStack` (valid only during `UPDATE_IN_PROGRESS`; creates cannot be cancelled and the feedback says so); `building` → `StopBuild`. AWS may still finish; the terminal outcome reflects what AWS did. `UPDATE_ROLLBACK_FAILED` → `rollback-failed, manualRecoveryRequired:true` with failing resources; the runbook offers `ContinueUpdateRollback` with `ResourcesToSkip` as a privileged action requiring `iac:approve`. `DeletionPolicy: Retain` resources are reported with `retained:true`. Runbook when the graph-serving stack is damaged: the orchestrator and status documents live in a separate stack, so `StartExecution` can be invoked from an operator workstation with the break-glass role; the substrate is restored with `npx serverless deploy` from a tagged revision (4.10); status documents are plain JSON in S3.

## 4.10 Bootstrap and substrate evolution

- **Substrate** = graph-server stack, IaC orchestrator stack, Auth0 tenant configuration, S3 buckets, the editor static site. It is deployed by conventional CI (GitHub Actions with OIDC → a deploy role, `npx serverless package` then `deploy`; package first because a failed build exits 0 and produces no artifact [memory note]) — **never by the IaC component** (denied by policy 3 above). Runtime/security patches (Node runtime, isolated-vm, yjs, scheduler 2.1.x) ship this way with the usual tests (§8.1).
- Schema evolution: `meta.schemaVersion` in every doc [FACT `schema.ts`, GE-07] + `Revision.schemaVersion`; readers support N and N-1; a migration is an admitted `system` mutation recorded in audit (PB-122); old revisions remain interpretable because projections are stored per revision.
- Admission service deploy: blue/green by Lambda alias is unnecessary for stateless functions; the risk is a *policy* regression, mitigated by the policy test suite and by `policyVersion` stamping (a bad policy can be rolled back by redeploy; audit shows which decisions used it).
- Recovery credentials: a break-glass IAM role (MFA, no console programmatic access), documented out-of-band; Auth0 emergency admin.
- Persistence: enable S3 versioning + lifecycle on the graph bucket (deleted objects recoverable for 30 days), daily cross-region replication of `revisions/`, `components/`, `audit/`, `policy/` (D-8 retention); restore drill = rebuild TOC (`POST /toc/rebuild` exists [FACT]) and verify a sample revision digest.
- Graphs evolving independently of the substrate: the projection `schemaVersion` gate (4.7.4) makes a lagging domain refuse activation explicitly instead of misinterpreting.
